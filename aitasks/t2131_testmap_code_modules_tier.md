## Goal

Add a **two-level code-module tier** (module → submodule) to the `ait testmap`
design and engine. It sits between "tests mapped to the changed files" and
"the full suite": a selection can be widened to run *all tests of the code
modules a change affects*, and the completion policy can run at module scope.

Today testmap has no such concept. Every map edge is test → source **file**
(`<path>[#member][@variant]` → repo-relative path). Annotation grammar v3
(`unit kind covers area scope trigger reads axis reviewed runner needs batch`)
has no module key. Selection has only two outcomes, *selected* or *full*
(completion policy `full | selected | auto`). Nothing in
`aidocs/testing_engine/n014_explorer_006_proposal.md` mentions a module or
component tier, not even to exclude or defer it.

## What already exists (reuse, do not duplicate)

- **Gradle modules (M2.3, landed).**
  - `deps.GradleModule{Name, Dir, BuildFile, Deps}`, `Graph.Modules()` and
    `Graph.ModuleOf(path)` (deepest dir wins): `goengines/internal/testmap/deps/deps.go:69-75`,
    `graph.go:118-151`.
  - Today they feed only the dependency closure and runner sets; they are
    never persisted or exposed.
  - A `gradle-dynamic` build widens a module's deps to every module (`deps/gradle.go`).
- **File-level dependency graph.** `Graph.Reverse`, `Closure`, `Opaque` and
  `FileFacts.Unresolved` (`deps/graph.go`, `deps/deps.go`) give the evidence
  needed to derive module→module edges for any language.
- **Areas (M2.5, landed).**
  - Flat named glob sets: `registry/scoped.go:60-66`, stored in
    `aitestmap/registry/areas.yaml`.
  - Allowed only on broad tests (integration/e2e/device). They are refused on
    unit-kind blocks (p1853_5 R7; proposal ~L2875).
  - `areas --import-codemap` reads `aitasks/metadata/code_areas.yaml` (already
    two-tier: `{name, path, children}`, agent-described via aitask-contribute's
    codemap sub-workflow, generated by `.aitask-scripts/aitask_codemap.sh`) and
    **flattens** `children` (`registry/areas_import.go`), losing the hierarchy.
- **Hand rules** (`when:` → `select:`) can express a module rule today, but only by hand.
- **Strict loaders.**
  - A new registry table must be registered: `RegisterHandTable` / `RegisterFile`
    in `goengines/internal/testmap/registry/load.go:106-116`.
  - A new annotation key is a grammar change in `goengines/internal/testmap/annot/grammar.go`.
  - `aitestmap/config.yaml` ignores unknown keys (additive).
- **Go** already works per package (`static:package`). Python packages are known
  to the scanner only for import resolution.

## Decisions taken during exploration (user-confirmed)

1. **Priorities.**
   - First: (a) an on-demand **widening tier** on `select` / `test`
     (e.g. `--widen submodule|module`), and (b) a **`module` completion-policy
     mode** next to `full | selected | auto`.
   - Later optimization: per-module execution batching (e.g. one `./gradlew :core:test`).
   - Unmapped / opaque / empty-selection fallback **stays full-suite** unless the
     module boundaries and cross-module dependencies give enough evidence that a
     narrower run is safe.
2. **Which modules a module-scope run includes.**
   - Use **evidence-based reach**: the touched modules, plus each dependent module
     that has a file reaching a changed file through the reverse dependency closure.
     An edit internal to a module does not pull in its dependents; an edit to its
     public surface does.
   - Each affected module then runs its **complete test set**.
   - Do **not** expand recursively through module dependencies just because a
     module was included.
   - **Keep** individually selected tests that lie outside those modules (the
     widening only adds tests).
   - Widen conservatively where the uncertainty can be bounded. Fall back to
     **full** otherwise: `gradle-dynamic`, opaque files, unresolved references
     the closure cannot follow.
3. **Test → module membership.**
   - A test may belong to **multiple** modules.
   - Defaults come from build structure and path containment. The modules of a
     test's **covered sources** count **even when path membership exists**.
     This matters for flat test dirs: in this repo `tests/` holds tests whose
     sources live in `.aitask-scripts/`.
   - Explicit annotations (e.g. `testmap:module`) **correct** the inference
     rather than being required.
   - **Unresolved membership stays visible** (a report line or check finding);
     it is never guessed silently.
4. **Modules vs areas.**
   - **Separate concepts.** Modules are a two-level *structural* grouping; areas
     remain *broad-test impact scope*.
   - Reuse the existing scanning and glob machinery.
   - **No independently maintained duplicate definitions.** Modules are
     *inferred* by providers: Gradle, Go and Python packages, the
     `code_areas.yaml` codemap keeping its two tiers, and agent proposals. They
     are persisted as a generated, **inspectable** table (pattern:
     `_scanned.yaml` + hand files), with hand `modules:` entries as
     **overrides** only.
   - An area may **reference modules** by name.
   - Inferred boundaries must be inspectable (a listing/explain verb) and overridable.
5. **Naming.**
   - Use `module` / `submodule` in CLI and YAML.
   - In the design prose, call M1–M10 **implementation work packages** to remove
     the collision (task file names and ids stay as they are).
   - State in the design that code modules are **logical source groupings**:
     build-system modules can seed them but need not define their boundaries
     exactly. At most two tiers.

## Where it plugs into the planned trail (`art:trail-testmap-feature`)

- **New registry table + inference + membership.** M2-style engine work on
  landed foundations (M2.1/M2.3/M2.5/M2.6). It can start without waiting on M4.
- **Selector widening.** Lives in M4.1 (`internal/selectr`, t1855; still
  undecomposed, no plan), so its coarse planning should absorb the tier, or a
  child here should depend on the M4.1 child. The output vocabulary
  (`SELECTED:`, `explain` reasons) needs a module-widening reason.
- **Completion mode.** M8.4 (t1859_4, Postponed) owns
  `completion.mode` and the `result="MODE:<full|selected>|…"` line. A `module`
  mode extends that not-yet-landed contract. M8.5 (`auto`/cadence) and M4.4
  `readiness` (`POLICY:` line) must learn it too.
- **Onboarding (M6, t1857).** `detect` / `classify` should surface inferred
  modules for review. The M6.5 skill is the natural place for an agent to
  propose or correct module boundaries.
- **Design doc.** Amend `aidocs/testing_engine/n014_explorer_006_proposal.md`
  with the module tier (data model, membership, selection grade, completion
  mode, onboarding), the decisions above, and the work-package rename.
  Re-check the t1812 decision "not hand-typed basic/deep/deepest labels and
  not profile tiers" (t1812:56): this tier is data-derived structure, not a
  hand label, and the amendment should say so explicitly.
